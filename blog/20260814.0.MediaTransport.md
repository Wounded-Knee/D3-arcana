# Stage One: Media Transport

**Date:** 14 August 2026

## Objective

We continued Stage One by adding group audio calls to the communication system.

The objective was to introduce media transport without rebuilding the existing HTTP, event, or WebSocket boundaries. Call lifecycle remains application state. Media packets remain a replaceable infrastructure concern.

The most important outcome is that a conversation can now host a durable audio call: members join through the API, receive LiveKit credentials, hear one another, and see participant changes in realtime through the same event pipeline used for messages.

## Call State

We added durable call records to PostgreSQL.

A conversation may have at most one active call. That constraint is enforced by a partial unique index on `calls.conversation_id` where `status = 'active'`.

The new tables are:

```text
calls
call_participants
```

A call contains:

```text
id
conversation_id
started_by
status
media_mode
started_at
ended_at
```

A participant contains:

```text
call_id
user_id
role
joined_at
left_at
```

`media_mode` is currently `audio`. The schema already admits `video` so the media path can expand without another structural rewrite.

## Transactional Call Events

Call mutations use the same transactional outbox pattern as messages.

Creating a call, joining, leaving, and ending a call all persist application state and the corresponding outbox event in one transaction:

```text
call.started
call.participant.joined
call.participant.left
call.ended
```

Those events are now first-class members of the `@d3-arcana/events` `DomainEvent` union, with Zod schemas shared by the server and clients.

## HTTP API

We added conversation-scoped call routes under `/api/v1`.

```text
POST   /api/v1/conversations/:conversationId/calls/join
POST   /api/v1/conversations/:conversationId/calls/leave
GET    /api/v1/conversations/:conversationId/calls/active
```

Join requires authentication and conversation membership. If no active call exists, the first join creates one and returns `201`. Subsequent joins return `200` with credentials for the existing room.

Join credentials include a short-lived LiveKit token, the client-reachable signaling URL, and the requested role (`publisher` or `subscriber`).

Leave marks the participant as departed. When the room becomes empty, a grace timer (default 45 seconds) ends the call and deletes the media room so a brief disconnect does not tear the session down immediately.

## Media Provider

Media remains behind a `MediaSessionProvider` interface:

```text
ensureRoom
endRoom
issueJoinCredentials
verifyWebhook
checkHealth
```

The development implementation is LiveKit. The server talks to the LiveKit control plane on loopback (`LIVEKIT_URL`) and advertises a LAN-reachable WebSocket URL to clients (`LIVEKIT_PUBLIC_URL`, or `ws://<preferred-lan-ip>:7880` when that override is omitted).

A mock provider exists for automated tests so call routes and health checks do not require a running SFU.

## LiveKit Webhooks

LiveKit reports room occupancy independently of the HTTP leave path.

The server accepts signed webhooks at:

```text
POST /webhooks/livekit
```

Handled events:

```text
participant_joined  → cancel empty-room grace; record the participant
participant_left    → mark left; maybe schedule grace
room_finished       → end the call if it is still active
```

This keeps durable call state aligned with the actual media room when a client disconnects without calling leave.

## Realtime Delivery

A new WebSocket consumer broadcasts call events to conversation members using the same idempotent consumption pattern as `message.created`.

The resulting path is:

```text
HTTP join / leave / webhook
        │
        ▼
  Call repository
        │
 ┌──────┴──────┐
 ▼             ▼
PostgreSQL   Outbox
               │
               ▼
        Background worker
               │
               ▼
            EventBus
               │
               ▼
        WebSocket clients
```

Clients therefore learn that a call started, that someone joined or left, and that the call ended, without polling.

## Health

We split process liveness from dependency readiness.

```text
GET /health            process is up
GET /health/database   PostgreSQL reachable
GET /health/livekit    LiveKit control plane reachable
GET /health/ready      both dependencies healthy
```

`/health/ready` returns `503` when either dependency fails. The mobile client polls this endpoint and shows a banner when the API, database, or LiveKit is unavailable.

## Development Networking

LAN development no longer depends on baking `192.168.x.x` into client environment files.

The mobile app infers API, WebSocket, and LiveKit hosts from the Metro packager host (`--lan`). The server prefers a physical NIC address over Docker/virtual interfaces when advertising LiveKit to clients.

Development CORS now allows private-network origins on Metro ports `8081` and `19006`, so LAN-wide Expo web can call the API.

LiveKit runs with Docker host networking so ICE UDP binds on the PC rather than Docker NAT. `pnpm dev:livekit` supplies the current default-route IPv4 as `--node-ip`.

## Mobile Client

The conversation screen now hosts the first group-audio vertical slice.

The client can:

```text
see an active call and its participants
join and receive LiveKit credentials
connect a platform-specific CallSession
mute / unmute
leave
react to call.* events over the existing WebSocket
```

`CallSession` is a small platform interface. Web uses `livekit-client`. Native development builds use `@livekit/react-native`. Expo Go continues to support chat; native calls require a development build because LiveKit native modules are not available in Expo Go.

API requests now resolve the base URL at call time and time out after 10 seconds, which avoids stale packager-host URLs after a network change.

## Automated Tests

The server suite now covers:

```text
call repository and outbox events
call HTTP routes
empty-room grace timer
LiveKit provider URL/room helpers
health routes
LAN address selection
development CORS for private-network origins
```

## Portability

LiveKit is a development media implementation, not a domain dependency.

Call records, participant membership, and temporal call events live in PostgreSQL and `@d3-arcana/events`. Another SFU can implement `MediaSessionProvider` without changing join/leave semantics or the client conversation model.

## Current Status

The following additional work is now complete:

- Durable `calls` and `call_participants` schema, with one active call per conversation
- Transactional `call.started`, `call.participant.joined`, `call.participant.left`, and `call.ended` events
- Authenticated join, leave, and active-call HTTP routes
- `MediaSessionProvider` abstraction with a LiveKit implementation
- Signed LiveKit webhooks for occupancy and room teardown
- Empty-room grace period before ending a call
- WebSocket delivery of call events to conversation members
- Dependency health endpoints for PostgreSQL and LiveKit
- Dockerized LiveKit SFU for local development
- Expo conversation-screen audio calls on web and native development builds
- Metro/LAN host inference for API and media URLs
- Development CORS for LAN Expo web

## Next Step

Stage One now has text and group audio flowing through the same durable, event-driven communication layer.

The next likely work includes video on the existing `media_mode` path, richer in-call participant UI, production identity, and replacing the local LiveKit stack with a production media provider behind the same interface.

The objective remains:

> **Record human communication in a durable, structured, event-driven system while preserving the natural communication experience—and establish the foundation from which a future semantic model can emerge without rebuilding the communication layer.**
