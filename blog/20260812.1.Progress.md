# Stage One: Communication Backbone

**Date:** 12 August 2026

## Objective

We continued development of Stage One of the project.

The objective was to turn the initial project foundation into a functioning communication backend.

The most important architectural goal was to establish a reliable event pipeline that can support future semantic processing without requiring the communication system to be rebuilt.

## PostgreSQL

We established PostgreSQL as the durable database for the application.

A dedicated application database and database role were created:

```text
database: d3_arcana
role:     d3_arcana_app
```

The server connects through environment configuration rather than relying on local development authentication.

We introduced Drizzle ORM and Drizzle Kit for database schema management and migrations.

The database now contains:

```text
users
conversations
conversation_members
messages
outbox_events
event_consumptions
```

The initial communication entities are therefore represented as durable relational state.

## Conversations and Messages

We implemented repositories for the principal communication objects.

A conversation consists of a durable conversation record and its members.

Conversation creation is transactional. The conversation and its initial membership are created together.

Messages are also persisted through a repository.

A message contains:

```text
id
conversation_id
sender_id
content
created_at
edited_at
deleted_at
```

A test message has been successfully created through the server and verified in PostgreSQL.

## Transactional Outbox

We then established an important boundary between durable application state and temporal events.

When a message is created, the server performs both operations within the same database transaction:

```text
BEGIN

    create message

    create outbox event

COMMIT
```

The message and the record of the event therefore cannot become inconsistent because one succeeds while the other fails.

The outbox contains records representing events which still need to be published.

For example:

```text
message.created
```

can contain:

```text
aggregate_type: message
aggregate_id:   message-1
actor_id:       alice

payload:
    messageId: message-1
    content: "The bridge should have two lanes."
```

The original message remains durable application state.

The outbox record is the durable record that the corresponding temporal fact occurred.

## Concurrent Event Publication

We implemented a background outbox publisher.

The publisher claims unpublished events using PostgreSQL row locking and:

```text
FOR UPDATE SKIP LOCKED
```

This allows multiple publishers to operate safely without processing the same outbox row simultaneously.

The process is:

```text
1. Find eligible events.
2. Claim them.
3. Commit the claim.
4. Publish the events.
5. Mark successfully published events.
```

Claims have a lease so that an event can become eligible again if a publisher fails.

The system therefore uses an **at-least-once delivery model** rather than attempting to guarantee exactly-once delivery.

Concurrency testing was completed successfully.

## EventBus

We implemented an `EventBus` abstraction.

The initial implementation is an in-memory event bus.

This is intentionally an abstraction rather than a direct dependency on an AWS service.

The architecture can therefore eventually use an AWS event service, another cloud provider, or a local implementation without changing the domain/application layer.

The event flow is now:

```text
PostgreSQL
    │
    ▼
outbox_events
    │
    ▼
background publisher
    │
    ▼
EventBus
```

## Idempotent Consumers

Because event delivery is at least once, consumers must be able to safely receive the same event more than once.

We added an `event_consumptions` table.

Its important identity is:

```text
consumer + event_id
```

A consumer records which events it has successfully processed.

This gives us:

```text
event
  │
  ▼
consumer
  │
  ├── already processed → ignore
  │
  └── new → process → record
```

The mechanism has been implemented and tested.

This will become particularly important when the semantic processing system is introduced. A semantic event must not accidentally be interpreted twice merely because the underlying event was delivered twice.

## Realtime Communication

We added WebSocket support using the portable `ws` implementation.

The WebSocket server shares the same Node HTTP server as Express.

The current endpoint is:

```text
/ws
```

A connecting client receives:

```json
{
  "type": "connection.ready"
}
```

We then connected WebSocket delivery to the event system.

`message.created` is now consumed by a WebSocket consumer.

The resulting architecture is:

```text
message.created
      │
      ├── test consumer
      │
      └── WebSocket consumer
                │
                ▼
        WebSocket manager
                │
                ▼
        connected clients
```

A message can therefore be created through the HTTP interface and subsequently appear on a connected WebSocket client.

## Background Processing

The event publisher originally required a temporary test endpoint to trigger publication.

We replaced that mechanism with a background worker.

The worker polls the outbox approximately once per second and publishes eligible events automatically.

The temporary endpoint:

```text
POST /test/events/publish
```

has now been removed.

The communication path is therefore genuinely asynchronous:

```text
HTTP request
     │
     ▼
durable message
     │
     ▼
durable outbox event
     │
     ▼
background publisher
     │
     ▼
EventBus
     │
     ▼
WebSocket clients
```

This was tested successfully.

## Architectural Result

We now have the first functioning event-driven communication backbone.

```text
                         HUMAN
                           │
                           ▼
                         HTTP
                           │
                           ▼
                    Message Repository
                           │
                    ┌──────┴──────┐
                    ▼             ▼
               PostgreSQL      Outbox
                                  │
                                  ▼
                           Background Worker
                                  │
                                  ▼
                              EventBus
                                  │
                         ┌────────┴────────┐
                         ▼                 ▼
                    Consumers         WebSocket
                                           │
                                           ▼
                                        Clients
```

The communication system is now separated into several independent concerns:

- durable state;
- temporal events;
- event publication;
- event consumption;
- realtime transport.

This separation is central to the future architecture.

The communication system does not need to know what future consumers will do with its events.

A future semantic processor can consume `message.created` without requiring the message system to understand semantics.

## Portability

Throughout this work we have maintained an explicit architectural requirement:

> **The system must not become locked into AWS.**

PostgreSQL, the EventBus, WebSocket transport, and storage-related interfaces are being treated as replaceable infrastructure.

AWS can eventually provide production implementations of these capabilities, but AWS-specific concerns should remain behind appropriate abstractions.

The application architecture should remain portable.

## Next Step

The backend now has enough infrastructure to begin defining the actual application-facing contracts.

Before beginning frontend development, the recommended next work is:

1. Formalize the HTTP API.
2. Formalize the WebSocket protocol.
3. Route realtime events by conversation rather than broadcasting to every connected client.
4. Implement conversation and message history retrieval.
5. Establish the authentication and identity boundary.
6. Add consistent runtime input validation.
7. Make the shared event package the authoritative event contract.
8. Add automated tests around the database, outbox, events, consumers, and WebSocket system.

After these boundaries are sufficiently stable, development can proceed to the Expo/React Native frontend.

The objective remains:

> **Record human communication in a durable, structured, event-driven system while preserving the natural communication experience—and establish the foundation from which a future semantic model can emerge without rebuilding the communication layer.**
