# Stage One: Client Integration

**Date:** 13 August 2026

## Objective

We completed the application-facing contract work for Stage One and integrated the first client.

The objective was to stabilize the HTTP and WebSocket boundaries established by the communication backbone, then verify that an Expo client can authenticate, load conversation history, send messages, and receive realtime updates through the existing event pipeline.

The most important outcome is that human communication can now flow end-to-end—from client input, through durable state and temporal events, to realtime delivery—without requiring ad hoc test endpoints or rebuild of the underlying architecture.

## HTTP API

We formalized the initial REST surface under `/api/v1`.

The API now includes:

```text
POST   /api/v1/users
GET    /api/v1/me
GET    /api/v1/users/:userId
GET    /api/v1/users/:userId/conversations
POST   /api/v1/conversations
GET    /api/v1/conversations/:conversationId
GET    /api/v1/conversations/:conversationId/messages
POST   /api/v1/conversations/:conversationId/messages
POST   /api/v1/conversations/:conversationId/members
```

Read access to conversations and message history now requires authentication and conversation membership. Message creation derives the sender from the authenticated user rather than from request body fields.

Message history supports cursor-based pagination through `limit` and `before`.

Structured error responses are used consistently across routes.

## Authentication

We established a portable authentication boundary through an `Authenticator` interface that resolves opaque bearer tokens to an `AuthenticatedUser`.

For development, a `DevelopmentAuthenticator` maps configured opaque tokens to existing database user IDs through `DEV_AUTH_TOKENS`.

Database seeding and token synchronization are supported through:

```text
pnpm --filter server db:seed
pnpm --filter server db:sync-auth
```

This keeps development credentials separate from production identity concerns while preserving a replaceable interface for a future real identity provider.

## WebSocket Protocol

We formalized the client/server wire format in `@d3-arcana/protocol`.

The connection sequence is:

```text
connect
  -> connection.ready
  -> auth.authenticate
  -> auth.authenticated
  -> conversation.join / conversation.leave
  -> wrapped domain events
```

Conversation join requires prior authentication and verified conversation membership. Domain events are delivered as wrapped `event` messages using the shared `@d3-arcana/events` envelope.

The WebSocket consumer applies the same idempotent consumption pattern used elsewhere, preventing duplicate broadcasts under at-least-once delivery.

## Event Contracts

We made `@d3-arcana/events` the authoritative source for domain event shapes.

The package now includes Zod schemas and a `DomainEvent` discriminated union. The outbox publisher validates event payloads at publication time rather than relying on unchecked casts.

This gives the server and clients a shared contract for temporal facts such as `message.created`.

## Automated Tests

We established a Vitest-based server test suite covering:

```text
repositories
transactional outbox behavior
EventBus and consumer deduplication
HTTP API routes
WebSocket authentication and routing
development CORS
```

The suite currently contains 44 tests and provides regression coverage for the contract and reliability mechanisms introduced during this phase.

## Mobile Client

We implemented the first Expo client vertical slice.

The mobile app includes:

```text
development login via opaque bearer tokens
conversation list
conversation message history
message send
realtime append via WebSocket
shared package consumption (@d3-arcana/events, @d3-arcana/protocol)
Metro monorepo configuration for workspace packages
```

The client resolves API and WebSocket hosts for web, emulator, and physical-device development contexts.

## Development CORS

Expo web required explicit cross-origin support because the web client and API server run on different local origins during development.

We added development-only CORS allowing Expo web origins and the headers required for bearer-token authentication. Automated tests now cover allowed origins, disallowed origins, and preflight behavior.

## Client Verification

The end-to-end vertical slice was verified on:

```text
Expo web
Android physical device via Expo Go (phone hotspot to development PC)
```

In both environments, the client successfully:

```text
reached the API
authenticated with development tokens
loaded conversation history
sent messages
received message.created events in realtime
```

## Operational Improvement

We added graceful shutdown handling for the development server process.

On `SIGINT` or `SIGTERM`, the server now stops the outbox worker, closes the HTTP server, and ends the PostgreSQL pool before exiting.

## Portability

Throughout this work we preserved the requirement that infrastructure remain replaceable.

PostgreSQL, the EventBus, WebSocket transport, authentication, and event contracts remain behind explicit abstractions. AWS and other providers can supply future implementations without rebuilding the communication layer.

## Next Step

Stage One now has a functioning client-integrated communication loop.

The next likely work includes expanding the mobile experience (creating conversations from the client, richer participant handling), introducing production-grade identity, and continuing operational hardening alongside further Stage One communication features such as media transport.

The objective remains:

> **Record human communication in a durable, structured, event-driven system while preserving the natural communication experience—and establish the foundation from which a future semantic model can emerge without rebuilding the communication layer.**
