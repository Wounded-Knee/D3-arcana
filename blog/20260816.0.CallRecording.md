# Stage One: Call Recording

**Date:** 16 August 2026

## Objective

We continued Stage One by making group audio durable and replayable without leaving the conversation timeline.

The previous media-transport work let members join a LiveKit room and hear one another. That audio disappeared when the call ended, and a late joiner could not hear what had already been said.

The objective was to copy each published microphone into object storage, index those copies in PostgreSQL, and play them on the existing multi-track timeline—during the call and after it. Tracks are never mixed. Audio bytes never enter the database.

The most important outcome is that a conversation now keeps a per-speaker recording that can be scrubbed, played, and caught up to live, on web and on an Android development build.

## Do Not Mix Tracks

LiveKit Track Egress copies one client microphone at a time (`startTrackEgress`). We do not use room-composite egress.

That constraint is load-bearing. A future semantic model needs to attribute speech to a person. A mixed file would erase that boundary.

Each recording session is therefore one user, one track, one object-key prefix.

## Object Store and Index

Audio lives in an S3-compatible store. Locally that is MinIO. PostgreSQL stores only the session and fragment index.

The new tables are:

```text
call_recordings
call_recording_fragments
```

A recording session contains:

```text
id
call_id
conversation_id
user_id
call_offset_ms
status
object_key
provider_egress_id
provider_track_sid
duration_ms
error
```

A fragment contains:

```text
id
recording_id
call_id
user_id
call_offset_ms
duration_ms
object_key
size_bytes
```

`call_recordings` is the open pipe. `call_recording_fragments` are the closed, playable clips. A session may stay `recording` while new clips continue to land.

A partial unique index allows only one `starting` or `recording` session per `(call_id, provider_track_sid)`.

The server writes through `OBJECT_STORE_ENDPOINT` on loopback. Presigned playback URLs advertise `OBJECT_STORE_PUBLIC_ENDPOINT` or `http://<preferred-lan-ip>:9000`. MinIO’s API now listens on `0.0.0.0:9000` so a phone on the LAN can fetch those URLs. The console stays on loopback.

## Ingest

LiveKit sends raw PCM over a websocket to the API:

```text
ws://127.0.0.1:3000/internal/egress
```

The pipe is authenticated with `EGRESS_INGEST_SECRET`. The payload is 48 kHz stereo `s16le`—LiveKit’s actual layout, not mono. We wrap each 500 ms of PCM in a WAV header and `put` it to MinIO.

Only a closed clip is playable. That leaves a half-second hole behind the live edge, which we accepted instead of rolling files or introducing LL-HLS.

Chat and ingest share one HTTP server. Two `WebSocketServer` instances on the same Node server broke `/ws`; a path router now upgrades `/ws` and `/internal/egress` separately.

## Recording Lifecycle

A published microphone starts a session. Egress failure and restore are durable outbox events, not only log lines:

```text
call.recording.started
call.recording.completed
call.recording.failed
call.recording.restored
```

A down MinIO or Egress worker does not block join. The call stays up; the timeline can show that a participant’s recording was interrupted and later restored.

LiveKit egress workers join the media room with identities such as `EG_…`. Those are not application users. Join, leave, and track webhooks ignore identities that are not user UUIDs, so Postgres is never asked to store `EG_…` in `call_participants.user_id`.

`room_finished` ends the durable call. It no longer calls `deleteRoom`; LiveKit has already torn the room down. Other LiveKit 404s (`not_found`, “does not exist”) are treated as already gone.

## HTTP and Ephemeral Realtime

Members can list calls and load recordings for a specific call:

```text
GET /api/v1/conversations/:conversationId/calls
GET /api/v1/conversations/:conversationId/calls/:callId
GET /api/v1/conversations/:conversationId/calls/:callId/timeline
GET /api/v1/conversations/:conversationId/calls/:callId/recordings
```

The recordings response includes presigned fragment URLs. Mid-call, new clips also arrive as ephemeral WebSocket messages (not outbox events):

```text
call.recording.fragment
call.catchup.safeToJoinLive
```

Clients may also poll recordings about once a second so a missed fragment still appears on the timeline.

## Catch-up

Scrubbing the past mutes live remote WebRTC so the listener is not hearing two times at once.

**Return to live** plays missed clips at 1.75×, then rides 1× at the ready edge (`now − 500 ms`). The API emits `call.catchup.safeToJoinLive` after about 600 ms of group silence in the still-open PCM buffers. **Jump to live** skips the remainder immediately and may clip a word.

Time selection on the timeline remains the attach point for a future annotation. Annotations themselves are out of scope.

## Timeline Playback

Playback is the existing multi-track timeline, not a detached player.

Web uses a small pool of `HTMLAudioElement`s. Android uses `expo-audio` (`createAudioPlayer`) with the same seek mapping: a clip is audible when the playhead sits inside `[callOffsetMs, callOffsetMs + durationMs]`. Metro resolves `playback-clock.native.ts` on the phone; a no-op native clock had made Play/Pause change only the button label.

An ended-call header no longer hides both Join and Start. If the call is live, the action is **Join call**. If it has ended, the action is **Start call** (the same `joinCall` path). A new `call.started` event clears the previous `endedAt` so Join appears immediately.

Android in-call audio defaults to the earpiece. A **Speaker** / **Earpiece** toggle calls LiveKit `AudioSession.selectAudioOutput`.

`expo-audio` is a native module. A development-build rebuild is required after adding it; a Metro reload is not enough.

## Automated Tests

The server suite now also covers:

```text
WAV header and fragment byte length (48 kHz stereo)
PCM fragment buffering and silence / catch-up math
persist-fragment indexing while a session is still recording
recording lifecycle start / fail / restore
recording seek mapping
object-store put and presigned read URLs
LiveKit webhook recording start/complete and non-user identities
call recordings HTTP response
```

## Portability

MinIO is a development object store, not a domain dependency. Another S3-compatible endpoint can implement `ObjectStore` without changing fragment semantics or the client timeline.

LiveKit remains the development SFU. Track egress is an implementation of “copy this microphone.” A different provider can supply the same per-track byte stream into the ingest websocket.

## Next Step

Stage One now records human speech as structured, per-person artifacts on the same timeline used to talk.

The next likely work includes time-range selection as an annotation attach point, production object storage and identity, and video on the existing `media_mode` path—still without mixing tracks.

The objective remains:

> **Record human communication in a durable, structured, event-driven system while preserving the natural communication experience—and establish the foundation from which a future semantic model can emerge without rebuilding the communication layer.**
